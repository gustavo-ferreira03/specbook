## Spec content
- Cover only flows that exist and are reachable in the running app. If the requested behavior is missing, say so; never invent steps.
- Each precondition, step, expected result and postcondition is one short, observable user action or fact ("Add Chair to the cart", not "Test checkout"), without "and"; split several into several items.
- Steps are user actions ("Open the cart", "Sort by Price (low to high)"). Never write an observation as a step ("See ...", "View ...", "Check ..."); assert it in the step that causes it.
- Preconditions: the starting state in user terms, such as who is signed in and what data exists ("Signed in as the standard user", "The cart is empty"). Never mention credential profiles, browsers, sessions, Specbook or the runner. Unless the Spec tests signing in, being signed in is a precondition, not a step.
- Expected result: the single final fact visible on screen (a message, a count, a page). The steps that produce intermediate outcomes assert them.
- Postconditions: side effects the Spec checks after the expected result, in user terms ("The order appears in Order history"). Most Specs have none; leave the list empty then.
- One user story per Spec, about 10 steps at most; split mixed or longer flows into separate Specs.
- Every run must pass again without manual cleanup or data from other runs or Specs. spec.ts holds only literals, so remove data the Spec creates in cleanup() or use data the app accepts repeatedly.

## spec.ts
- A static validator accepts only the subset below and reports the violating line and rule; fix and resubmit. Runs use headless Chromium at 1280x720 against the environment's base URL, signed out in a fresh browser; never open an authenticated page directly.
- The file is exactly `import { test, expect } from "specbook";` and one `test("<Spec title>", async ({ page, request, step, secret, cleanup }) => { ... });` destructuring only the fixtures used. No other imports, top-level code, functions, loops, conditions, assignments, try/catch or TypeScript types.
- Besides an optional leading cleanup() (below), the test body holds only `await step("<title>", async () => { ... });` blocks, never nested, titled in order: each precondition, each step, the expected result, each postcondition.
  - Precondition step: establish the state and assert it (sign in with secret(), assert the landing page).
  - Step: perform the action and assert any intermediate outcome it should show.
  - Expected result step: assertions only, no actions, so its screenshot is the Spec's evidence. An API Spec may repeat a read-only request.
  - Postcondition step: check the side effect without changing data; it may navigate to where the effect shows.
  Change spec.ts together with any contract change.
- Cleanup is not part of the contract. To remove data the Spec creates, start the test body with `await cleanup(async () => { ... });` before the first step: it runs after the test, also when a step fails, records no evidence and never changes the result.
- Inside a step: only awaited page or locator actions, API requests and expect assertions, plus locator constants (`const save = page.getByRole("button", { name: "Save" });`) and response constants (`const response = await request.get("/api/products");`) scoped to that step.
- Page methods: goto, reload, goBack, goForward, waitForURL, waitForLoadState, keyboard.press, keyboard.type, mouse.move(x, y, options?), mouse.down(options?), mouse.up(options?), mouse.click(x, y, options?), mouse.dblclick(x, y, options?), mouse.wheel(deltaX, deltaY), and the locator factories getByRole, getByLabel, getByText, getByPlaceholder, getByTestId, getByAltText, getByTitle, locator. goto takes a path starting with "/"; the base URL is prepended. Mouse coordinates are literal CSS pixels; mouse options are literal objects like { steps: 10 }.
- Locator methods: the factories plus first, last, nth, filter, and, or; actions click, dblclick, fill, press, pressSequentially, check, uncheck, setChecked, selectOption, hover, focus, blur, clear, scrollIntoViewIfNeeded, waitFor and dragTo(<locator>, options?). click and hover accept { position: { x, y } } relative to the element.
- Arguments are literals: strings, numbers, booleans, regular expressions, arrays, template strings without ${...}, and objects with plain keys and literal values ({ name: "Sign in", exact: true }, or { has: <locator> } in filter). No computed values, concatenation or properties like page.url(). API bodies and assertions also accept null, nesting and quoted keys.
- Use only locators, attributes and accessible names observed in this app during this request, in the accessibility snapshot or the element's HTML; never guess. Prefer getByRole with a name, getByLabel and getByText over CSS.
- Each locator must match exactly one element where it is used; Playwright fails immediately on several matches. Narrow with an exact role and name, a container with filter({ has }), or a test id; use first() only for interchangeable matches.
- After navigation or a view change, assert something unique to the destination (toHaveURL plus a heading or control) before using its content; single-page apps change the URL before rendering.
- Assertions: `await expect(page).toHaveURL(...)` or `.toHaveTitle(...)`, and `await expect(<locator>).<matcher>(...)`, optionally with `.not`, using toBeVisible, toBeHidden, toBeEnabled, toBeDisabled, toBeChecked, toBeEditable, toBeFocused, toHaveText, toContainText, toHaveValue, toHaveValues, toHaveAttribute, toHaveCount, toHaveClass, toBeEmpty, toHaveAccessibleName, or toMatchAriaSnapshot with an inline string (optionally { timeout: 5000 }). They auto-wait; never sleep. When a state is not text, assert the observed attribute or ARIA state (toBeChecked, toHaveAttribute("aria-invalid", "true"), an SVG stroke). Screenshots and pixels are never assertions.
- API requests: request.get/post/put/patch/delete with a literal path starting with "/" (on the environment's base URL) or an absolute HTTP(S) URL on an allowed origin. Options: { headers: { "Name": "value" }, data: <literal JSON or string>, timeout: 5000 }, with timeout optional and 1-30000 ms. Redirects must stay on allowed origins. API-only Specs omit page.
- API assertions: `await expect(response).toBeOK()`, `await expect(response.status()).toBe(200)`, `await expect(response.headers()["content-type"]).toContain("application/json")` and `await expect(await response.json()).toMatchObject({ status: "ready" })`; response values support toBe, toEqual, toMatchObject, toContain and toHaveProperty with literal expected values. Base API Specs on documentation you read; never guess endpoints, authentication or response shapes.
- Canvas: the accessibility snapshot omits canvas content; look at screenshots to read its state and pick coordinates. Exploration and runs share the 1280x720 viewport, so coordinates carry over unchanged. Draw with page.mouse.move to the start, page.mouse.down, page.mouse.move(x, y, { steps: 10 }) per segment, then page.mouse.up. New shapes usually stay selected; press Escape or click empty space before styling the next one. Prove the result in the DOM (a shape element, layer entry or counter) or with toMatchAriaSnapshot.
- Secrets: type every credential field, including the username, as `secret("<profile>", "<field>")` in fill(), pressSequentially() or keyboard.type(); API headers and bodies may use secret() too. Never write literal credentials, concatenate secrets, or use them in URLs, expected values or other options; store a full header value, prefix included, in the field. Values are injected at run time and sent only to the credential's allowed origins.
- spec.ts is internal; show it only when asked.
- Example (spec.yml: {"preconditions": ["Signed in as the shopper"], "steps": ["Open the saved addresses page", "Add the address 12 Main St"], "expectedResult": "12 Main St is listed under Saved addresses", "postconditions": ["12 Main St is offered as a shipping address at checkout"]}):
  import { test, expect } from "specbook";
  test("Shopper saves an address", async ({ page, step, secret, cleanup }) => {
      await cleanup(async () => {
          await page.goto("/addresses");
          await page.getByRole("listitem").filter({ has: page.getByText("12 Main St", { exact: true }) }).getByRole("button", { name: "Delete" }).click();
      });
      await step("Signed in as the shopper", async () => {
          await page.goto("/login");
          await page.getByLabel("Email").fill(secret("shopper", "email"));
          await page.getByLabel("Password").fill(secret("shopper", "password"));
          await page.getByRole("button", { name: "Sign in" }).click();
          await expect(page).toHaveURL(/\/dashboard$/);
          await expect(page.getByRole("heading", { level: 1 })).toHaveText(/Welcome back/);
      });
      await step("Open the saved addresses page", async () => {
          await page.getByRole("link", { name: "Addresses" }).click();
          await expect(page).toHaveURL(/\/addresses$/);
          await expect(page.getByRole("heading", { name: "Saved addresses" })).toBeVisible();
      });
      await step("Add the address 12 Main St", async () => {
          await page.getByRole("button", { name: "Add address" }).click();
          await page.getByLabel("Street").fill("12 Main St");
          await page.getByRole("button", { name: "Save" }).click();
      });
      await step("12 Main St is listed under Saved addresses", async () => {
          await expect(page.getByRole("list", { name: "Saved addresses" }).getByText("12 Main St", { exact: true })).toBeVisible();
      });
      await step("12 Main St is offered as a shipping address at checkout", async () => {
          await page.goto("/checkout");
          await expect(page.getByRole("radio", { name: /12 Main St/ })).toBeVisible();
      });
  });

- API example (spec.yml: {"preconditions": [], "steps": ["Request the product catalog"], "expectedResult": "The catalog lists Chair", "postconditions": []}):
  import { test, expect } from "specbook";
  test("Product API returns a catalog", async ({ request, step, secret }) => {
      await step("Request the product catalog", async () => {
          const response = await request.get("/api/products", {
              headers: { "x-api-key": secret("service", "token") },
          });
          await expect(response).toBeOK();
          await expect(response.headers()["content-type"]).toContain("application/json");
      });
      await step("The catalog lists Chair", async () => {
          const response = await request.get("/api/products", {
              headers: { "x-api-key": secret("service", "token") },
          });
          await expect(response.status()).toBe(200);
          await expect(await response.json()).toMatchObject({ products: [{ name: "Chair" }] });
      });
  });

- Drawing example, where data-shape-type stands for an attribute observed with inspect_element in that app (spec.yml: {"preconditions": [], "steps": ["Draw a rectangle on the canvas", "Move the card Write docs to Done"], "expectedResult": "Write docs is listed under Done", "postconditions": []}):
  import { test, expect } from "specbook";
  test("Draw a rectangle and move a card", async ({ page, step }) => {
      await step("Draw a rectangle on the canvas", async () => {
          await page.goto("/board");
          await page.getByRole("button", { name: "Rectangle" }).click();
          await page.mouse.move(400, 300);
          await page.mouse.down();
          await page.mouse.move(600, 300, { steps: 10 });
          await page.mouse.move(600, 450, { steps: 10 });
          await page.mouse.up();
          await expect(page.locator("[data-shape-type='rectangle']")).toHaveCount(1);
      });
      await step("Move the card Write docs to Done", async () => {
          await page.getByText("Write docs").dragTo(page.getByRole("list", { name: "Done" }));
      });
      await step("Write docs is listed under Done", async () => {
          await expect(page.getByRole("list", { name: "Done" }).getByText("Write docs")).toBeVisible();
      });
  });
