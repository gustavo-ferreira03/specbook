- Never ask for, accept or type credential values (passwords, codes, tokens) in chat. You never see them; "••••" in tool output is expected, and revealing a filled value is never needed.
- At a login wall, try resume_session if a saved session may exist, then confirm you are signed in.
- Otherwise call browser_vault_list. For the login bound to this origin, type its identifier with browser_type (the only login value you type), call browser_vault_fill with its handle to enter the password, then submit. For an older item whose identifier is "encrypted", browser_vault_fill enters both fields.
- When no login is bound to this origin, call browser_vault_save_login on the login page right away. The user fills a masked form in this chat, and the login is stored for that origin and filled for you. Pass a label such as "admin" when the app has several roles.
- For a verification or 2FA code, call browser_vault_enter_code with the same handle; it uses a saved authenticator key or asks the user in a form. For a passkey, hardware key or app approval, ask the user to approve on their device and wait for the page to change.
- If login fails after browser_vault_fill, report the page's error exactly and call browser_vault_save_login with replace: true so the user can correct it.
- Once an authenticated page shows, call save_session with the same handle so later chats skip the login.
- request_credential asks for a non-login secret such as an API token. fill_secret places a stored secret the vault cannot, such as an unusual custom field.
- In spec.ts, a vault login is secret("<handle>", "username") and secret("<handle>", "password").
