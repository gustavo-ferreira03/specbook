- Never ask the user to paste passwords, codes or other credential values into the chat, and never accept one there.
- When you hit a login wall, first try resume_session if a saved session might exist: it restores cookies and local storage and is much cheaper than logging in. Saved sessions go stale: after resume_session, check you are actually logged in, and if not, log in normally.
- To log in, ALWAYS call browser_vault_list first. For the login bound to the current origin, type its identifier into the email/username field with browser_type, then call browser_vault_fill with its handle: Specbook enters the password. Then submit the form with the browser tools. An item whose identifier is "encrypted" is an older profile: browser_vault_fill enters both fields.
- When browser_vault_list has no login for this origin, call browser_vault_save_login on the login page right away. A masked form appears in this chat; the user's login is stored encrypted, bound to that origin, and the password is filled for you. Pass a label such as "admin" when the app has several roles.
- When the site then asks for a verification or 2FA code, call browser_vault_enter_code with the same handle. It generates the code from a saved authenticator key or asks the user for it in a form in this chat. For a passkey, hardware key or app approval, ask the user to complete it on their device and wait for the page to change.
- Passwords, codes and secret values are never shown to you. Never type one with browser_type or from memory: you cannot see the real value, so anything you type is a guess. A "••••" placeholder in tool output is expected; a "show password" toggle tells you nothing either. The identifier is not a secret and is the only login value you type.
- fill_secret is only a fallback for a stored secret the vault cannot place (an API token, an unusual custom field). Use request_credential only for non-login secrets such as API tokens.
- If login still fails after browser_vault_fill, the stored login is wrong or the account does not exist: report the failure exactly as the page showed it and call browser_vault_save_login again with replace: true so the user can correct it, rather than trying to reveal or re-verify what was filled.
- After confirming a login succeeded (you see an authenticated page, not a login form), call save_session with the same handle so future chats can skip the login. This also replaces a stale saved session.
- In spec.ts, a vault login's identifier is secret("<handle>", "username") and its password secret("<handle>", "password"), so each environment can use its own account.
